# RollHelperLauncher MVP

Минимальный WPF-лаунчер на .NET 8 для универсальных пакетов RollHelper.

Текущая версия исходников: `0.1.16`. Актуальная общая карта проекта находится в `../docs/CODEMAP.md`.

## Что уже делает

1. Загружает `release-manifest.json` по HTTP/HTTPS.
   Источник перечитывается из `launcher.config.json` при каждом обновлении списка, поэтому старый URL не остаётся в памяти после самообновления.
2. Показывает доступные пакеты без брендовой логики.
3. Скачивает выбранный ZIP.
4. При наличии `sha256` проверяет контрольную сумму.
5. Безопасно распаковывает пакет в версионную папку.
6. Читает `package.json` из корня ZIP.
7. Запускает описанный в пакете `entrypoint`.
8. Записывает все действия и ошибки в `launcher.log`.
9. Проверяет наличие новой версии самого лаунчера и обновляет её одной кнопкой.
10. Показывает дополнения отдельно под выбранной программой.
11. Проверяет зависимости и минимальную версию основной программы.
12. Устанавливает, включает, отключает и полностью удаляет дополнения.
13. Показывает строки программ и дополнений как полноценные интерактивные элементы с hover, выбором и статусом.
14. Сохраняет размер окна, положение разделителя и ширину колонок после перезапуска и самообновления.
15. Различает установку, включение и обновление дополнения: для новой версии уже установленного дополнения кнопка называется «Обновить».

## Где хранятся файлы

- Пакеты: `%LOCALAPPDATA%\Programs\RollHelper\Packages\<id>\<version>`
- Кэш: `%LOCALAPPDATA%\Programs\RollHelper\Cache`
- Состояние дополнений: `%LOCALAPPDATA%\Programs\RollHelper\State\packages.json`
- Разметка лаунчера: `%LOCALAPPDATA%\Programs\RollHelper\State\launcher-ui.json`
- Лог: `%LOCALAPPDATA%\RollHelper\Logs\launcher.log`
- Конфигурация источника: `launcher.config.json` рядом с EXE

Если `launcher.config.json` отсутствует, используется:

`https://github.com/voffkazxc/RollHelper/releases/latest/download/release-manifest.json`

## Формат ZIP-пакета

`package.json` должен находиться непосредственно в корне ZIP. Рядом размещаются файлы пакета и его entrypoint.

Примеры манифестов находятся в папке `examples`.

## Сборка

```powershell
dotnet build .\RollHelperLauncher\RollHelperLauncher.csproj -c Release
```

Для переносимой одиночной сборки без установленного .NET:

```powershell
dotnet publish .\RollHelperLauncher\RollHelperLauncher.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true
```

Полный релиз RollHouse вместе с самообновляемым лаунчером собирается из корня репозитория:

```powershell
.\packaging\build-release.ps1 -Version 0.1.10
```

Если изменился только интерфейс или логика лаунчера, RollHouse пересобирать и повышать его версию нельзя. Такой релиз сохраняет пакеты из предыдущего манифеста и собирает только новый лаунчер:

```powershell
.\packaging\build-launcher-release.ps1 `
  -Version 0.1.10 `
  -PackagesManifestPath .\previous-release-manifest.json `
  -PackageAssetBaseUrl https://github.com/voffkazxc/RollHelper/releases/download/v0.1.8/
```

Относительные ссылки пакетов из старого манифеста преобразуются в абсолютные. Поэтому новый релиз лаунчера не требует повторно загружать ZIP бренда и не показывает ложное обновление RollHouse.

Поле `launcher` в `release-manifest.json` содержит версию, прямую ссылку на ZIP и SHA-256. В шапке всегда видна отдельная кнопка проверки обновления самого лаунчера. Если версия новее установленной, кнопка меняется на «Обновить лаунчер до …». После нажатия архив проверяется, лаунчер закрывается, заменяет свои файлы и запускается снова. Кнопка выбранной программы подписана отдельно, например «Обновить RollHouse и запустить». Пользовательские пакеты, настройки и логи находятся вне папки лаунчера и не перезаписываются.

При запуске правая панель дополнений скрыта. Она открывается только после ручного выбора программы. Чтобы закрыть её, можно нажать «Скрыть», клавишу `Esc` или щёлкнуть по пустому месту в списке программ. Ширину панелей можно менять перетаскиванием разделителя, а ширину колонок таблиц — за границы заголовков.

Размер окна, положение разделителя и ширина колонок сохраняются автоматически при закрытии. Файл разметки находится вне папки EXE, поэтому обновление лаунчера его не перезаписывает. Выбранная программа намеренно не запоминается: после запуска дополнения остаются скрытыми до ручного выбора программы.

## Зависимости и дополнения

Дополнение имеет тип `module`, указывает основную программу через `extends` и при необходимости задаёт минимальные версии зависимостей:

```json
{
  "id": "rollhouse-calling",
  "type": "module",
  "displayName": "Автообзвон",
  "version": "1.0.0",
  "extends": "rollhouse",
  "requires": [
    { "id": "rollhouse", "minVersion": "0.1.8" }
  ]
}
```

Лаунчер не знает, что делает модуль. Он устанавливает пакет, записывает состояние `enabled` в `State\packages.json` и сразу применяет изменение к основной программе из поля `extends`. Оператор не должен вручную нажимать Reload после установки, включения, отключения или удаления дополнения. Если основная программа уже установлена, лаунчер запускает её установленную версию повторно; для AHK-пакетов это должно работать через штатный `#SingleInstance Force` или аналогичный механизм самого бренда.

## Границы текущей версии

Лаунчер пока не выполняет миграции конфигов и не делает автоматический откат. Эти возможности можно добавлять поверх текущего универсального формата пакетов.

## Будущие дополнения

Лаунчер не должен знать особенности RollHouse, RollClub или другого бренда. Каждый компонент описывает себя в манифесте одним из универсальных типов:

- `brand` — основная программа бренда;
- `module` — устанавливаемое дополнение;
- `tool` — самостоятельный служебный инструмент.

Дополнение указывает идентификатор основной программы через поле `extends`, а совместимую версию — через `requires`. После выбора программы интерфейс показывает видимый раздел «Дополнения» с кнопками установки, отключения и удаления. Контекстное меню по правой кнопке повторяет эти действия как дополнительный быстрый способ.

При добавлении нового бренда или модуля меняется только содержимое манифеста и ZIP-пакета. Код лаунчера и его логика остаются общими.

Любой новый бренд обязан поддерживать безопасное повторное применение: повторный запуск entrypoint не должен создавать второй рабочий экземпляр и должен перечитать состояние включённых модулей. Это часть контракта бренда, а не ручное действие оператора.

Правила кодировки, масштаба Windows 100/125/150% и проверки интерфейса перед релизом: `../docs/OPERATOR_UI_COMPATIBILITY.md`.
