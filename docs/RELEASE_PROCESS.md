# Как выпускаются обновления RollHelper

## Что считается обновлением

Исходники в репозитории — единственный источник правды. Файлы внутри `%LOCALAPPDATA%\Programs\RollHelper` являются установленными копиями. Их можно временно менять для проверки, но такое изменение не считается готовым обновлением и будет потеряно при следующей установке.

У каждого компонента своя версия:

- `launcherVersion` — интерфейс лаунчера;
- `rollhouseVersion` — основной пакет RollHouse;
- `reportLoadVersion` — дополнение «Отчёт — нагрузка»;
- `catalogVersion` — версия списка, который скачивает лаунчер.
- `catalogBaseRelease` — предыдущий полный каталог. Все бренды и дополнения, которые этот релиз не меняет, переносятся из него без пересборки и без изменения версий.

Если изменился только отчёт, повышаются `reportLoadVersion` и `catalogVersion`. Если изменился основной `main.ahk`, сервер или общая логика RollHouse, повышаются `rollhouseVersion` и `catalogVersion`. Версия лаунчера меняется только при изменениях самого лаунчера.

Перед публикацией всегда указывается актуальный `catalogBaseRelease`. Это защищает другие бренды и дополнения: выпуск RollHouse не должен удалять RollClub или его модули из общего списка.

Если в новом каталоге меняется только дополнение, ZIP RollHouse повторно не собирается и не публикуется. В `package-release.json` указывается прежняя версия `rollhouseVersion` и поле `rollhouseReuseRelease` с номером релиза, где уже лежит нужный ZIP RollHouse. Новый manifest ссылается на прежний ZIP и его SHA-256. Так оператор увидит обновление только у дополнения.

Пример такого запроса находится в `packaging/examples/package-release-module-only.example.json`.

## Порядок выпуска

1. Изменить исходный файл в репозитории.
2. Проверить работу и синтаксис.
3. Обновить нужные версии в `packaging/package-release.json`.
4. Зафиксировать изменения в Git и отправить их в `master`.
5. Выполнить:

   ```powershell
   .\packaging\publish-package-release.ps1 -Publish
   ```

6. В лаунчере нажать «Обновить список программ».
7. Для изменённого компонента появится состояние «Доступно обновление» и отдельная кнопка обновления.

После установки или изменения дополнения оператор не должен вручную перезагружать AHK. Лаунчер применяет изменение универсально: берёт `extends` у модуля и повторно запускает установленную версию родительской программы. Брендовый entrypoint обязан безопасно обработать повторный запуск и перечитать состояние модулей. Если меняется сама основная программа, оператор нажимает её кнопку обновления/запуска в лаунчере.

## Что увидит оператор

- Изменился лаунчер: появляется кнопка «Обновить лаунчер до …».
- Изменился RollHouse: строка RollHouse показывает доступное обновление.
- Изменилось дополнение: обновление появляется только у этого дополнения под RollHouse, а кнопка называется «Обновить».
- Простое закрытие и повторное открытие окна без установки обновления ничего нового показывать не должно.

Правила внешнего вида и совместимости экранов находятся в `docs/OPERATOR_UI_COMPATIBILITY.md`. Они обязательны для новых брендов и модулей.

Перед любым выпуском обязательно выполнить `docs/RELEASE_GUARDRAILS.md`. Этот документ запрещает случайно менять уже опубликованные бренды и дополнения при добавлении нового пакета.
