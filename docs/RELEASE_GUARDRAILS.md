# Защита опубликованных пакетов от регрессий

Этот документ обязателен для любого человека или агента, который меняет `release-manifest.json`, создаёт релиз или добавляет бренд/дополнение.

Цель: новый RollClub, модуль или исправление текста **не должны менять, переустанавливать, ломать или визуально портить уже работающий RollHouse**.

## Главное правило

Каждый пакет независим.

- `brand` меняется только при изменении самого бренда;
- `module` меняется только при изменении самого дополнения;
- `launcher` меняется только при изменении лаунчера;
- `catalog` меняется только при изменении списка пакетов или их метаданных.

Новый пакет не даёт права пересобирать, заменять или менять версию другого пакета.

Пример: добавление RollClub и его F4-модуля не должно менять ZIP RollHouse, ZIP «Отчёт — нагрузка», их версии, SHA-256 или состояние установки у оператора.

### Эталон Ctrl+F4 для RollClub

Режим дежурства RollClub должен сохранять поведение последней рабочей версии до лаунчера (`fa81822`): первый поиск UIA может быть холодным, следующие опросы используют сохранённую `Панель данных` и не обходят всё дерево Syrve повторно.

- серверный путь RollClub находится в `brands/rollclub/server/rollclub_kc_legacy.py`;
- сборщик RollClub обязан направлять `/api/iiko/kc-list` в этот файл;
- нельзя заменять проверку живого кеша на `Exists()` или `IsOffscreen`: в Syrve это сбрасывало рабочий кеш на каждом цикле и увеличивало опрос примерно с `0,5 с` до `10–11 с`;
- нельзя переносить правила выбора заказа из RollHouse в RollClub: RollClub сохраняет свои проверки комментария `Пост`, передзвона, отменённого заказа и занятого оператора;
- запуск RollClub обязан остановить прежний процесс на порту `5000` и поднять сервер из того же установленного пакета, чтобы AHK не подключился к серверу другого бренда или старой версии.

Перед выпуском Ctrl+F4 обязательно проверить лог `bridge.log`: после первого успешного поиска последующие строки `KC-LIST LEGACY` должны содержать `cached=1`.

Пограничный адрес нельзя молча считать точным результатом KML. При расстоянии до границы до 100 метров, пересечении полигонов или геокодинге без номера дома интерфейс обязан показать предупреждение, не применять автоматическое время и записать `ZONE_UNCERTAIN` в `parse_debug.log`.

## Запрещено без отдельной задачи

Нельзя делать следующее «заодно»:

- пересобирать RollHouse при выпуске RollClub;
- повышать версию RollHouse, если менялся только модуль или каталог;
- переписывать URL или SHA-256 уже опубликованного RollHouse/модуля;
- менять названия, кодировку или данные чужого пакета через повторную сериализацию общего манифеста;
- трогать `%LOCALAPPDATA%\Programs\RollHelper\State\packages.json` или пользовательские файлы при публикации;
- возвращать RollClub к записи настроек в относительный `RkConfig.ini` или внутрь папки версии пакета;
- собирать `brands/rollclub/RkConfig.ini` через текстовый вывод PowerShell: исходник UTF-16 должен копироваться из Git как необработанные байты;
- включать или отключать дополнение у оператора автоматически;
- публиковать новый каталог, пока не проверены все сохранённые строки существующих пакетов.

Если требуется изменить RollHouse, это оформляется как отдельная задача: новая версия RollHouse, отдельный список изменений и ручная проверка обычного заказа.

## Правило «минимального радиуса»

Перед работой нужно письменно определить, какие ID пакетов разрешено менять.

| Тип задачи | Разрешённые изменения |
|---|---|
| Новый бренд | Только новый `brand`, его новые `module`, каталог |
| Новый модуль RollHouse | Только этот `module`, каталог |
| Исправление текста каталога | Только каталог |
| Обновление лаунчера | Только `launcher`, каталог |
| Исправление RollHouse | Только `rollhouse`, при необходимости его зависимые модули, каталог |

Всё, что не вошло в этот список, считается защищённым и должно остаться побайтно тем же ZIP либо ссылаться на прежний ZIP и SHA-256.

## Обязательная проверка манифеста

До публикации нового каталога нужно:

1. Скачать исходный `release-manifest.json` как UTF-8.
2. Изменить только разрешённые ID пакетов.
3. Для всех остальных пакетов сравнить поля `id`, `type`, `displayName`, `version`, `url`, `sha256`, `extends` и `requires` с исходным манифестом.
4. Сохранить новый файл строго как UTF-8 без BOM.
5. После публикации скачать **опубликованный** манифест, а не только локальный файл, и повторить сравнение.
6. Проверить, что URL и SHA-256 каждого старого пакета остались прежними и файл по URL отвечает `200`.

Особое правило для кириллицы: нельзя передавать названия пакетов через клиент, который угадал неверную кодировку. Для проверки надо открыть скачанный файл с явной UTF-8-кодировкой и убедиться, что видны `Отчёт — нагрузка` и `Дежурство заказов (Ctrl+F4)`, а не набор `Ð...`.

## Проверка оператора после выпуска

Перед тем как сообщать «готово», проверяются именно затронутые сценарии.

### Если добавлен новый бренд

- существующий RollHouse остаётся со своей прежней версией и статусом;
- его дополнения видны только после выбора RollHouse;
- новый бренд виден отдельно и не выбран сам по себе;
- модуль нового бренда не установлен автоматически;
- установка нового бренда не меняет состояние RollHouse.

### Если обновлён только модуль

- у бренда нет статуса «Доступно обновление»;
- статус «Доступно обновление» виден только у нужного дополнения;
- кнопка действия у дополнения называется «Обновить»;
- остальные дополнения и базовый бренд не меняют версию.

### Если обновлён только каталог

- не появляются новые версии брендов или модулей;
- не меняются установленные ZIP;
- исправляется только список и его текст;
- оператору сообщают, что достаточно нажать «Обновить список программ».

## Публикация и кэш GitHub

`releases/latest/download/release-manifest.json` может несколько минут отдавать предыдущий файл из кэша. Это не повод выпускать ещё один случайный пакет и не повод говорить, что обновление уже видно.

После публикации нужно:

1. Проверить релиз через `gh release list`.
2. Проверить манифест по прямому URL версии: `.../releases/download/vX.Y.Z/release-manifest.json`.
3. Проверить `latest/download` отдельно.
4. Если `latest` ещё старый, честно сообщить оператору, что нужно подождать кэш, а не просить переустанавливать бренд.

## Стандарт финального отчёта

В отчёте всегда писать четыре вещи:

1. Что конкретно изменилось.
2. Что сознательно **не менялось**.
3. Что оператору нажать в лаунчере.
4. Какие ручные проверки остаются.

Запрещён общий ответ «готово», если не сказано, какие пакеты затронуты и какие сохранены без изменений.
