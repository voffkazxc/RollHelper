# Контракты стабильного поведения RollHelper

Этот документ обязателен для любого человека или агента, который меняет рабочую логику, лаунчер, пакет бренда или дополнение. Его задача — не позволить локальному исправлению сломать уже работающий сценарий.

Документ описывает не желаемую архитектуру, а проверяемые свойства текущей системы. Если код им противоречит, нельзя молча переписывать контракт под код: сначала нужно выяснить, это регрессия или согласованное изменение поведения.

## Порядок чтения перед работой

1. `docs/CODEMAP.md` — где находится рабочий код.
2. Этот документ — что считается стабильным поведением.
3. `docs/RELEASE_GUARDRAILS.md` — какие пакеты разрешено выпускать.
4. README конкретного дополнения.
5. Только затем — `STATUS.md`, планы, архивы и старые версии.

Архив, установленная копия и старый portable-пакет не являются источником правды. Они используются только как эталон поведения или материал для сравнения.

## Правило минимального изменения

Перед редактированием агент обязан записать:

- какой пользовательский сценарий меняется;
- какие package ID разрешено менять;
- какие сценарии защищены и не должны измениться;
- какими тестами и журналами будет доказан результат.

Если исправляется один модуль, нельзя «заодно» переделывать соседние горячие клавиши, сервер, зоны, тему, настройки или упаковку другого бренда.

## Границы пакетов

| Пакет | Что в нём живёт | Что нельзя делать |
|---|---|---|
| `rollhouse` | Базовый RollHouse | Менять при выпуске RollClub или отдельного дополнения |
| `rollclub` | Базовый процесс `engine_rollclub.ahk`, сервер RollClub и встроенные обработчики разрешённых модулей | Считать, что изменение маркерного дополнения само заменит код внутри бренда |
| `rollhouse-report-load` | Отдельный исполняемый отчёт | Поднимать версию RollHouse только из-за изменения отчёта |
| `rollclub-duty` | Разрешение режима `Ctrl+F4`; рабочая логика выполняется в основном процессе RollClub | Запускать второй AHK-процесс, который параллельно управляет Syrve |
| `rollclub-call-auto-accept` | Разрешение режима `Ctrl+F2`; рабочая логика выполняется в основном процессе RollClub | Исправлять обработчик только в ZIP дополнения и забывать обновить пакет `rollclub` |
| `rollclub-first-order-gunkan` | Разрешение акции первого заказа | Пробивать Гункан при выключенном дополнении |
| `rollclub-refund` | Отдельное окно формирования возврата | Автоматически отправлять или изменять заказ |
| `rollclub-zones` | KML и данные зон RollClub | Встраивать пользовательскую карту в случайное обновление основного бренда |
| `launcher` | Установка, обновление, запуск и состояние пакетов | Добавлять знания о внутренней логике конкретного бренда |

Критичный вывод: `modules/rollclub-call-auto-accept/rollclub_call_auto_accept.ahk` является маркером. Обработчик `Ctrl+F2`, UIA-поиск и индикация находятся в `engine_rollclub.ahk` и `lib/IikoUI.ahk`. Изменение этой логики требует новой версии пакета `rollclub`, даже если версия маркерного дополнения не меняется.

## Защищённые сценарии оператора

### RollHouse

- тильда открывает пульт и читает текущий заказ;
- `F1` выполняет СІВ;
- Enter переносит подготовленные значения;
- `Ctrl+Enter` подтверждает заказ и сохраняет его на точку;
- F5 работает только при установленном дополнении отчёта;
- отключённый модуль не должен оставлять активную горячую клавишу или фоновый таймер.

После изменения RollHouse эти сценарии проверяются вручную на обычном заказе. Нельзя считать тесты парсера полной заменой проверки Syrve.

### RollClub

- тильда открывает пульт и читает текущий заказ;
- `F1` выполняет СІВ;
- Enter переносит подготовленные значения;
- `Ctrl+Enter` завершает заказ;
- `Ctrl+F4` доступен только с дополнением дежурства;
- `Ctrl+F5` доступен только с дополнением возврата;
- `Ctrl+F2` доступен только с дополнением автоприёма звонка.

Одна горячая клавиша не имеет права запускать или продолжать другой сценарий. Дежурство, СІВ, ввод заказа и звонок не должны управлять Syrve одновременно.

## Контракт `Ctrl+F2`: автоприём звонка RollClub

Состояния режима:

1. `Вимкнено` — таймер не работает, звонок не принимается.
2. Одно нажатие `Ctrl+F2` — режим переходит в `Очікую дзвінок`.
3. Повторное нажатие до звонка — оператор вручную выключает режим.
4. При появлении активной кнопки `Принять` или `Прийняти` режим принимает один звонок.
5. После успешного клика режим автоматически выключается.

Обязательная обратная связь:

- после переключения показывается заметное экранное сообщение;
- у пункта автоприёма в трее стоит галочка, пока ожидание активно;
- в открытом пульте написано `АВТОПРИЙОМ: ОЧІКУЮ ДЗВІНОК`;
- после принятия звонка пульт и трей возвращаются в выключенное состояние.

UIA/WinAPI-контракт:

- сначала используется стабильный `AutomationId=btnPbxCallAccept`, а видимые названия `Принять` и `Прийняти` остаются резервным поиском;
- используется активный видимый элемент с нативным HWND;
- UIA один раз получает нативный HWND кнопки, после чего частый цикл проверяет состояние только лёгким WinAPI `IsWindowEnabled`;
- повторный обход UIA-дерева разрешён только при потере HWND и не чаще одного раза в 2 секунды;
- запрещено опрашивать UIA-свойства кнопки каждые 100–250 мс: такой цикл загружает UI-поток Syrve и делает ручное редактирование заказа медленным;
- клик выполняется через UIA или нативное сообщение по HWND;
- изображения и координаты для этой функции запрещены.

Журнал: `RollHelper\logs\rollclub_call_auto_accept.log` внутри установленной версии RollClub. Значимые события: `waiting_started`, `waiting_stopped`, `call_detected`, `call_accepted`.

Если в журнале есть `waiting_started`, горячая клавиша сработала. Если сразу следом есть `waiting_stopped operator`, оператор нажал комбинацию второй раз. Если есть `call_detected`, но нет `call_accepted`, неисправен клик, а не горячая клавиша.

## Контракт `Ctrl+F4`: дежурство RollClub

- режим включается и выключается только оператором;
- после найденного и открытого заказа дежурство прекращается;
- режим не должен сам возобновляться внутри заказа, во время тильды, Enter, F1 или `Ctrl+Enter`;
- первый UIA-поиск может быть холодным, последующие опросы используют живой кеш;
- запрещено проверять кеш через `Exists()` или `IsOffscreen`, потому что Syrve сбрасывал такой кеш и возвращал задержку 10–11 секунд;
- отдельный процесс дополнения не должен параллельно нажимать Syrve.

Эталон и серверный путь зафиксированы в `docs/RELEASE_GUARDRAILS.md`.

## Контракт UIA и WinAPI

1. Стабильный `AutomationId` или осмысленный `Name` предпочтительнее координат.
2. Временный числовой ID нельзя выдавать за постоянную привязку.
3. Элемент `Элемент редактирования` без контекста недостаточен: нужна конкретная ячейка, кнопка или путь.
4. `CurrentBoundingRectangle` возвращает экранные координаты. Любой fallback-клик обязан использовать тот же режим координат.
5. Кеш UIA допустим только при доказанной стабильности элемента. Динамические кнопки, вкладки и строки таблицы требуется переполучать.
6. Рекурсивный обход всего дерева Syrve в рабочем цикле запрещён. Он допустим в диагностическом сканере, но не в F1, Enter, `Ctrl+F2` или `Ctrl+F4`.
7. Если UIA не сработал, нельзя сообщать оператору об успехе только потому, что команда клика не вернула ошибку. Нужна проверка результата или однозначный журнал.
8. Координатный fallback удаляется только после ручной проверки новой UIA-привязки на реальном окне Syrve.

## Контракт интерфейса оператора

Каждое фоновое или переключаемое действие должно отвечать на четыре вопроса прямо в интерфейсе:

- команда принята или нет;
- что сейчас делает система;
- завершилось ли действие;
- что оператор должен сделать при ошибке.

Нельзя оставлять только скрытый журнал для обычного действия. Краткая индикация обязательна для ожидания звонка, дежурства, обновления, длительного чтения и применения дополнения.

Подробные правила масштаба, кириллицы и расположения элементов находятся в `docs/OPERATOR_UI_COMPATIBILITY.md`.

## Пользовательские данные и обновления

Нельзя перезаписывать при обновлении:

- `%LOCALAPPDATA%\Programs\RollHelper\State\packages.json`;
- `%LOCALAPPDATA%\Programs\RollHelper\State\launcher-ui.json`;
- `%LOCALAPPDATA%\Programs\RollHelper\UserData\<brand>\`;
- пользовательские KML, цены зон, PLU, горячие клавиши и WinAPI-привязки;
- операторские журналы, если они нужны для разбора последнего сбоя.

Файлы внутри `Packages\<id>\<version>` считаются неизменяемой установленной версией. Ручной патч такой папки допустим только для диагностики и обязательно переносится в исходники, тест и новый релиз.

После установки, включения, отключения или удаления дополнения лаунчер сам перезапускает родительский бренд. Оператор не должен знать про `Reload This Script`.

## Известные ловушки, которые нельзя повторять

| Ошибка | Что происходило | Защита |
|---|---|---|
| AHK v2-синтаксис в проекте AHK v1.1 | Скрипт не перезагружался | Проверять AHK v1 через `AutoHotkeyU64.exe /ErrorStdOut /iLib NUL script.ahk`; ключ `/syntaxCheck` в v1 не поддерживается |
| UTF-8 без BOM для AHK v1 | Кириллица превращалась в `Р...` | Все AHK-файлы релиза сохранять UTF-8 с BOM |
| Экранные координаты UIA при оконном `Click` | Клик уходил в другое место | Явный одинаковый `CoordMode` или нативный HWND |
| Кеш неактивной кнопки PBX | `Ctrl+F2` включался, но звонок не принимался | Переполучать активный control при входящем звонке |
| Несколько нажатий toggle-клавиши | Режим включался и сразу выключался | Видимая индикация состояния и журнал переходов |
| Изменение маркерного модуля без бренда | В лаунчере модуль обновлён, рабочий код прежний | Проверять, где фактически выполняется обработчик |
| Рекурсивный UIA-поиск в цикле | Задержки до 10–20 секунд | Однократный поиск, кеш и точечное обновление |
| Правка установленной папки | Следующее обновление уничтожало исправление | Исходник + тест + новый ZIP + manifest |
| Повторная сборка чужого пакета | Рабочий RollHouse ломался при выпуске RollClub | Правило минимального радиуса и сравнение manifest |
| Скрытое подтверждение под окном настроек | Оператор думал, что кнопка не работает | Все диалоги поверх родительского окна |
| Две копии AHK/сервера | F4 вмешивался в F1 и заказ | Один основной процесс бренда и явное завершение старого сервера |

Каждая новая повторяемая ошибка добавляется в эту таблицу вместе с автоматической проверкой или конкретным пунктом smoke-теста.

## Обязательные доказательства перед фразой «готово»

### Любое изменение AHK

1. Точечные unit-тесты изменённой функции.
2. `AutoHotkeyU64.exe /ErrorStdOut /iLib NUL script.ahk` для изменённых entrypoint и include-файлов.
3. Проверка отсутствия дубликатов горячих клавиш и переменных GUI-control.
4. Ручной сценарий в Syrve либо честная пометка, что он ещё не выполнен.

### Изменение RollClub

1. `python -m unittest discover -s tests -p 'test_rollclub_*.py'`.
2. Тильда, F1 и `Ctrl+Enter` не изменились.
3. Проверяется только затронутое дополнение: его включение, выключение и повторный запуск бренда.
4. Журналы подтверждают переходы состояний, а не только отсутствие окна ошибки.

### Изменение лаунчера

1. Сборка WPF без предупреждений и ошибок.
2. Тесты жизненного цикла модулей и самообновления.
3. Проверка процесса: после запуска кнопка показывает `Остановить`, после выхода из AHK не позднее чем через секунду возвращается `Запустить`.
4. Проверка на 100%, 125% и 150% масштабе.

Состояние бренда определяется только по `runtime.primaryExecutable` из его `package.json`. Фоновый Python-сервер, оставшийся после закрытия AHK, не означает, что бренд запущен. Кнопка `Остановить` завершает все процессы пакета, включая сервер. При запуске другого бренда лаунчер сначала останавливает текущий бренд и только затем запускает выбранный. Специальных имён RollClub или RollHouse в этой логике быть не должно.

### Публикация

1. Изменена версия только нужного пакета и каталога.
2. Незатронутые строки manifest совпадают с предыдущим релизом.
3. Опубликованный ZIP скачивается, его SHA-256 совпадает.
4. Проверены прямой URL релиза и `latest/download`.
5. Оператору дан точный путь обновления и список ручных проверок.

## Как документировать следующий сложный фикс

После исправления нужно записать пять фактов:

1. Наблюдаемый симптом.
2. Подтверждённая причина, а не предположение.
3. Изменённый контракт или сохранённый контракт.
4. Добавленный тест и журнал, по которым ошибка видна.
5. Версия пакета и результат ручной проверки оператором.

Если хотя бы один пункт неизвестен, исправление ещё не считается закрытым.
